# Task disclosure — all seven benchmark tasks

Full disclosure of every task prompt, fixture and expected artifact
literal used across the benchmark tracks. Prompts are quoted **verbatim**
from `evaluation_v2.TASKS` (set A) and `evaluation_v3.TASKS_B` (set B);
expected values are the literals enforced by `evaluation_v2.validate()`
and `evaluation_v3.EXPECTED`.

## Shared protocol context

- Model: `deepseek-flash`, temperature 0, max output 1,200 tokens.
- Uniform tracks (`run_v2`, `run_native_mcp`, `run_native_highbudget`):
  set A tasks; `execute_code`-style tool or native MCP tools.
- v3 track (`run_v3`): set B tasks on six conditions — `python`,
  `calcside`, `docker`, `e2b`, `openshell`, `calcside_mcp` — with
  64 model / 96 tool call caps and graph recursion limit 512.
- Budgets differ by track: v2 official (`results/v2-agent`) and the
  baseline native MCP run (`results/v2-native-mcp`) used 8 model / 12
  tool calls; the native high-budget replication
  (`results/v2-native-mcp-highbudget`) used 64 / 96, and all six v3
  conditions in `results/v3-agentic` — uniform backends and
  `calcside_mcp` alike — used 64 / 96 with graph recursion limit 512.
  See each run's `manifest.json`.
- Success = the persisted artifact validates (`evaluation_*.validate`),
  independent of the model's final answer. Fetch/public-field checks do
  not prove HTTP provenance.
- Supplementary track (`run_openai_sol.py`,
  `results/openai-sol-agentic`): the same set-B tasks on the two
  Calcside conditions only (`calcside`, `calcside_mcp`), 3 tasks ×
  3 repetitions × 2 conditions = 18 trials with `gpt-6.1-sol` over the
  OpenAI Responses API (`reasoning_effort="medium"`, 16,384-token
  output cap including reasoning, temperature omitted) — see
  `PROTOCOL_OPENAI_SOL.md`. Generation budgets differ from the
  DeepSeek runs; not a matched-budget comparison.

## Set A — four short data tasks (`evaluation_v2.TASKS`)

Used by: `results/v2-agent`, `results/v2-native-mcp`,
`results/v2-native-mcp-highbudget` (and preflights).

### A1. `stats`

Prompt (verbatim):

> Read data.csv (header x). Write result.json as a JSON object with count, mean and max of column x. Use numbers, not strings.

Inputs: `data.csv` — header `x` plus integers 1..100 (generator:
`"x\n" + "".join("%d\n" % n for n in range(1, 101))`,
`evaluation_v2.py`). 294 bytes.
Artifact: `result.json`.
Expected (from `validate()`): `{"count": 100, "mean": 50.5, "max": 100}`.

### A2. `join`

Prompt (verbatim):

> Join employees.csv to departments.csv on dept_id. Sum salary by department name. Write summary.json as a JSON object mapping each department name to its numeric total. Do not include extra keys.

Inputs (verbatim file contents):

`employees.csv`:

```csv
name,dept_id,salary
Ada,1,100
Bob,2,90
Chen,1,110
```

`departments.csv`:

```csv
dept_id,name
1,Engineering
2,Sales
```

Artifact: `summary.json`.
Expected: `{"Engineering": 210, "Sales": 90}` (exact key set).

### A3. `file`

Prompt (verbatim):

> Create squares.csv with header n,sq and exactly five rows, ordered n=1 through 5, with sq=n*n. Read it back to check your work.

Inputs: none.
Artifact: `squares.csv` — exact expected content is the CSV
`[["n","sq"],["1","1"],["2","4"],["3","9"],["4","16"],["5","25"]]`.

### A4. `fetch`

Prompt (verbatim):

> Fetch https://api.github.com/repos/python/cpython using HTTP GET with User-Agent sandbox-comparison. Write repo.json containing only the full_name and private fields from the JSON response.

Inputs: none. Requires egress to `api.github.com` (per-backend policy
differs — see REPORT/README for each backend's network posture).
Artifact: `repo.json`.
Expected: `{"full_name": "python/cpython", "private": false}` (exact key
set). Validates public fields only, not HTTP provenance.

## Set B — three agentic tasks (`evaluation_v3.TASKS_B`)

Used by: `results/v3-agentic` (all six conditions, 54 trials).
Fixtures are generated by functions/constants in `evaluation_v3.py`;
`run_v3.py` also writes the full materialized inputs to
`results/v3-agentic/task-inputs.json`.

### B1. `triage` — multi-file enumeration + tie-break

Prompt (verbatim):

> The directory logs/ contains JSONL files. Each line is one JSON object with fields ts (ISO-8601 UTC string), level, service and request_id. Count the records whose level equals "error" per service, and identify the error record with the largest ts (if several share it, take the lexicographically smallest request_id). Write triage.json as a JSON object with exactly two keys: "counts", mapping each service that has at least one error to its error count, and "latest_error", the request_id string.

Fixture recipe — `_log_files()` in `evaluation_v3.py`:

- 10 files `logs/part-00.jsonl` … `logs/part-09.jsonl`, 20 lines each.
- Line `i` of part `p` has `n = p*20 + i` (0..199) and is a compact JSON
  object (`separators=(",",":")`) with:
  - `"ts": "2026-11-01T00:%02d:%02dZ" % (n // 60, n % 60)`
  - `"level": "error"` iff `n % 7 == 0 and n % 5 != 0`, else `"info"`
  - `"service": services[n % 3]` where `services = ["api", "worker", "render"]`
  - `"request_id": "req-%04d" % n`
- **Tie fixtures** (appended verbatim to `logs/part-09.jsonl`):

```json
{"ts":"2026-11-01T00:04:00Z","level":"error","service":"render","request_id":"req-tie-z"}
{"ts":"2026-11-01T00:04:00Z","level":"error","service":"api","request_id":"req-tie-a"}
```

Both share the maximum `ts`; `req-tie-a` < `req-tie-z`
lexicographically, so `latest_error` must be `req-tie-a`.
Total fixture size: 10 files, 17,599 bytes.
Artifact: `triage.json`.
Expected (`evaluation_v3.EXPECTED`):
`{"counts": {"api": 9, "worker": 8, "render": 8}, "latest_error": "req-tie-a"}`.

### B2. `reconcile` — two-file join with unmatched sets

Prompt (verbatim):

> ledger.csv has columns id,amount. bank.csv has columns id,amount,status. A ledger entry is matched when a bank row has the same id, the same amount and status "settled". Every other id is unmatched on its own side. Write reconcile.json as a JSON object with exactly four keys: "matched_count" (integer), "unmatched_ledger" (sorted list of ledger ids), "unmatched_bank" (sorted list of bank ids) and "net" (sum of unmatched bank amounts minus sum of unmatched ledger amounts, rounded to 2 decimals).

Inputs (verbatim constants `LEDGER`/`BANK` in `evaluation_v3.py`):

`ledger.csv`:

```csv
id,amount
TX01,100
TX02,50.50
TX03,200
TX04,75
TX05,10
TX06,300
```

`bank.csv`:

```csv
id,amount,status
TX01,100,settled
TX02,50.50,settled
TX03,210.10,settled
TX04,75,pending
TX06,300,settled
TX07,40,settled
```

Artifact: `reconcile.json`.
Expected: `{"matched_count": 3, "unmatched_ledger": ["TX03", "TX04",
"TX05"], "unmatched_bank": ["TX03", "TX04", "TX07"], "net": 40.1}`.

### B3. `series` — bounded-context aggregation over 5,000 rows

Prompt (verbatim):

> series.csv has columns idx,value with 5000 rows. Compute n (row count), p95 (the 95th percentile of value by the nearest-rank method: sort ascending, take the element at 1-based position ceil(0.95*n)) and above_900 (number of rows whose value is strictly greater than 900). Write series_stats.json as a JSON object with exactly three integer fields: n, p95, above_900. Do not print the whole file.

Fixture recipe — `_series_rows()`/`SERIES` in `evaluation_v3.py`:

- Rows: `"%d,%d" % (i, (i * 37) % 1000)` for `i` in `range(5000)`.
- File: `"idx,value\n"` + rows joined by `\n` + trailing `\n`.
- **Size: 43,350 bytes.** This is a moderate-size batch task — it
  exercises bounded-context aggregation, NOT streaming, NOT a
  large-data guarantee, and makes no claim about bigger inputs.

Artifact: `series_stats.json`.
Expected: `{"n": 5000, "p95": 949, "above_900": 495}`.

## Where the inputs live

| Task | Authoritative definition | Materialized copy |
|------|--------------------------|-------------------|
| A1–A4 | `evaluation_v2.TASKS` (inline literals/generators) | staged per-trial into each backend workspace; set-A manifests record file hashes only |
| B1 triage | `evaluation_v3._log_files()` | `results/v3-agentic/task-inputs.json` (full contents, written by a run) |
| B2 reconcile | `evaluation_v3.LEDGER`, `evaluation_v3.BANK` | `results/v3-agentic/task-inputs.json` |
| B3 series | `evaluation_v3._series_rows()` / `SERIES` | `results/v3-agentic/task-inputs.json` |

Datasets under `results/` are produced by a run and are not committed;
the generators above are the authoritative definition.

`run_v3.StagedBackend.setup` writes each fixture via the backend's own
`execute` and verifies by exact `read_file` round-trip before the agent
loop starts; staging failures are recorded as `setup_error`, never
silently retried.

apply: op.#Apply & {...}

CUE 里没有用户定义的函数。它不是函数，是一份数据。

那它怎么就跑起来了？

模板语言

模板语言本来就是用来少写代码的

CUE

KubeVela 的 component / trait 抽象，一个 Application 底下几十个 k8s 对象，收成一份配置。

component: { type: "webservice" }

HCL

Terraform module。同样的 VPC 写八遍，抽出来只写一遍。

module "vpc" { ... }

Starlark

Bazel 的构建规则写成函数，能复用，能组合。

def cc_library(name, srcs):
这类语言还有个共同点：纯。CUE 不能发 HTTP，Starlark 不能 open 文件。所以模板里那些“能做事”的东西，没有一个是语言自带的，全是宿主塞进去的。

纯度一开始是为了可预测、可校验，不是为了安全。但它顺带产生了一个结果：代码在被宿主执行之前，什么都干不了。

语言里没有 HTTP文件环境变量 都在宿主手里

模板语言不产生副作用，它只描述副作用该发生在哪。

工作流 DSL

引擎遍历数据，执行 op，再把结果填回去

CUE valuecueflow 遍历执行器output unify下游唤醒
workflow.cueKubeVela
apply: op.#Apply & {
  value: { ... }
}

status: op.#Read & {
  value: { ... }
}

执行器做真实世界的事：apply 一个 k8s 资源，发一个 HTTP 请求，调一次外部 API。

副作用不在 CUE 里。CUE 每次求值都是纯的，脏活全在引擎里，发生在两轮求值中间。

状态全在 value 里，所以 workflow 可以停：序列化存下来，下次读出来接着填。
求值纯 · 无副作用
执行执行器 · 真实世界
求值结果 unify 回来
执行器是注册进来的。模板能做的事，永远不超过宿主已经提供的能力。
边界 · KubeVela

作者可信，环境不可信

01

op 是副作用点

workflow 引擎负责调度、并行、等依赖；op 只负责在那一刻产生副作用。命令式操作全关进 op，op 外面尽量都是能推导、能校验的数据。

02

统一的是数据

CUE 的 unify 让不同来源的 schema 在同一份 value 里共存、互相约束。

写模板的是平台工程师，是可信的。不可信的是运行环境的复杂度。边界画在“声明式”和“命令式”之间。

互操作 · host ↔ guest

宿主和 guest 之间，边界是漏的

好处：guest 里的一等公民

Go 把能力注册成 Starlark builtin。net.post 就是一次普通调用，值直接映射，不用序列化，也不用跨进程。

r = net.post(url=..., body=...)

坏处：内存边界不清晰

Go 的分配器不按实例记账。guest 的值就活在宿主的 GC 堆上，一个乘法就能把进程吃掉。

"x" * 10**9 # max_steps 限不住
KubeVela 不在乎：作者可信，互操作只是为了把 op 的结果填回 value。calcside 在乎：作者不可信，内存不隔离就是漏洞。
语言边界builtin · 值映射 · 同一条线程
进程边界subproc · 一个实例一个进程
OS 边界cgroup v2 · OOM 只杀它
语言层只能限步数和能力；内存要靠进程和 cgroup 补。

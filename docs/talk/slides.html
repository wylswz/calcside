Capabilities are the boundary

Agent writes StarlarkSees only granted globalsGate · guest ↔ hostPolicy before / afterAudit
01

Capability fs · net · io

The only way to cause side effects. fs is a quota-bound VFS; net has a host allowlist and injects secrets at send time, so scripts can reference them but never read them.

02

Ext ext.tavily.search()

Pure Starlark, never native binaries. Extensions compose base capabilities, and every inner call crosses the Gate again, inheriting allowlists, secrets, and audit.

03

Policy Rego · builtin.*

Veto any op before or after it runs. Server policies always apply; user policies are chosen per instance and snapshotted at creation. Private networks are blocked at dial time by default.

04

Instance spec · TTL · limits

One spec = capabilities + policies + limits. Globals and the VFS persist across executions; runs in-process or as one OS process per instance.

Why memory leaks through

01Guest and host interoperate; guest values live on the host's GC heap
02A GC can't attribute bytes to instances: no per-guest accounting
03max_steps bounds CPU, but not "x" * 10**9
04Approach 2 too: capture checking tracks capabilities, not bytes

calcside's trade-off

01One process per instance, capped by cgroup v2; OOM kills only it
02Lighter than a container: no image, no rootfs, no network namespace
03Bound before rendering; output, files, and artifacts are all capped
04Resource accounting falls back to the OS, not capabilities
